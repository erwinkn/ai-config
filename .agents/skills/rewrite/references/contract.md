# Contract

Reconstruct the final intended contract before fresh implementation. Each obligation has an id, statement, source, status (settled or unresolved), and an observable check or explicit limitation. Cover semantic results and operational properties that apply: error contracts, ordering, cancellation, idempotency, concurrency, persistence, migrations, backward compatibility, authorization, data safety, auditability, latency/resource constraints, accessibility, and rollout/rollback requirements. These are prompts for discovery, not mandatory invented features.

Read the original request, plan, existing PR, review history, tests, logs, and meaningful observed behavior. Do not assume that every current behavior is intended or every review suggestion was accepted. Distinguish original obligations, later accepted refinements, explicit compromises, accidental behavior, and open questions. A reviewer checks contract completeness before the new implementation is compared. Requirements and test oracles must not be authored solely from the new code.

The writing context starts at the target base with this contract and project architecture. It can inspect the old patch to resolve a specific missing fact, but must not use it as the scaffold for an incremental cleanup. Compare the whole new contribution, including side effects and failure paths, against the preserved contract. Keep the original candidate intact. Normal fresh review, verification, and audit apply before the replacement is considered merge-ready. Failure to show a real structural improvement is a valid experiment result, not a reason to replace the old PR anyway.
