# Evaluate

A small, optional comparison procedure rather than a benchmark platform.

## Assignment

lead.

Use the named agent definition for substantive delegated work. If you are already its assigned worker, execute this procedure directly; do not dispatch yourself again. Preserve the caller's endpoint and return mode. Read [shared rules](../principles/references/rules.md) and the relevant [principles](../principles/SKILL.md).

## Procedure

1. Choose a representative request and repository starting state. Write down the behavior the change is meant to affect and checks that must remain true.

2. Run baseline and candidate under comparable models, tools, authority, and context. Record the actual versions and interventions.

3. Inspect artifacts and outcomes; a fresh reviewer may compare anonymized results without seeing which version produced them.

4. Repeat when noise makes the result unclear. For a costly or subtle claim, optionally run identical copies first to estimate variability.

5. Record completion, defects, scope drift, time/cost where available, and whether the evidence supports adopting the change.

## Rules

- Do not edit the evaluation task or acceptance bar after seeing a convenient result.
- One success is useful feedback, not proof of general superiority.
- No mandatory A/A stage, external benchmark suite, or comprehensive run archive before ordinary use.

## Complete when

A useful supported comparison or an explicit inconclusive result is recorded.

## Examples

Keep a familiar repository revision and a small request that exercised the failure: a feature with a clear spec, a repair with a real repro, a noisy PR feedback case, a negative trigger, or a handoff/resume. Compare the same starting state and disclose model/tool changes or human interventions. Inspect the resulting change and evidence, not just the final prose. Repetition or an identical-baseline run is optional when needed to understand variability. Save the task, observations, and adoption decision as a small record.
