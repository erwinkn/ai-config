# Interfaces

Start from what a caller needs to accomplish and what it must know to use the result. A useful module hides substantial decisions behind an interface that is simpler than its implementation. Count invariants, ordering requirements, error modes, configuration, and relevant performance obligations as interface knowledge, not just method signatures. Test useful behavior at meaningful seams; do not introduce an abstract interface solely because a second implementation is imaginable. Prefer ownership by domain knowledge over files named for incidental execution phases. Remove pass-through layers when they add no leverage. Do not force every module below a fixed line count, and do not replace the project’s established domain language with a universal architecture glossary.
